查询优化：同一条 SQL，快慢天差地别

你写 SELECT * FROM student JOIN sc ... 时，数据库内部做了什么？为什么有时一瞬、有时半天？ 本章揭秘：查询的处理流程和 DBMS 的自动优化——考点集中在优化规则和代价估算。

一、查询处理的四个步骤

  1. 查询分析：词法、语法检查（SQL 写错在这一步报错）
  2. 查询检查：语义检查、权限检查，转为关系代数表达式（查询树）
  3. 查询优化：代数优化 + 物理优化，选出执行代价最小的方案
  4. 查询执行：按计划执行，返回结果
「查询优化是 DBMS 自动完成的」是判断题常客：用户写 SQL 时不需要指明执行路径（非过程化语言的价值所在），优化器负责找好方案。关系系统的优化技术：代数优化、物理优化两大类。

二、代数优化：启发式规则（必背）

优化器重排关系代数树，核心思想：尽早缩小数据量。五条启发式规则：

  1. 选择运算尽可能先做（把行数降下来，后面的运算全部受益）——最重要的一条
  2. 投影与选择同时做（避免重复扫描）
  3. 投影与其后/前的连接合并执行
  4. 把笛卡尔积改成连接（加上连接条件；笛卡尔积会产生 m×n 的巨量元组）
  5. 找出公共子表达式，只计算一次

例题：一条 SQL 的优化之旅

-- 原始写法（先笛卡尔积再筛选，代价巨大）
SELECT sname FROM student, sc WHERE student.sno = sc.sno AND sc.grade > 90;

-- 优化器理解过程：
-- ① 笛卡尔积 student × sc：4 学生 × 6 选课 = 24 行
-- ② 应用启发式规则：先做选择 σ(grade>90)，只剩 1 行；投影只留 sno
-- ③ 笛卡尔积改造为连接 ⋈
-- 代价从「大表全拼」降到「小集合连接」

三、物理优化：操作怎么执行

操作可选算法说明
选择全表扫描 / 索引扫描（B+树、哈希）有合适索引且选择率高时用索引，否则全表扫描反而更快
连接嵌套循环连接 / 块嵌套循环 / 排序-合并连接 / 索引连接 / 哈希连接代价取决于可用内存块数、有无索引、是否已排序
代价估算的基本单位是磁盘块 I/O 次数。经典计算题：给出表块数和内存可用块数，算嵌套循环连接需要读多少块——关键公式：外层读一遍 × 内层读一遍/每块外层元组。

四、动手实践：亲眼看看索引的威力

在本机 MySQL 中做同样实验效果更直观（有真实 I/O）：

USE school_practice;
CREATE INDEX idx_sage ON student(sage);
EXPLAIN SELECT * FROM student WHERE sage > 19;   -- 看 key 列显示 idx_sage，type=ref
-- 对比 DROP INDEX idx_sage ON student; 再 EXPLAIN：type=ALL（全表扫描）
