并发控制：多个事务同时跑，如何不打架

一百个用户同时买票、同时转账——DBMS 让事务并发执行来提效率，但并发会制造新问题。 本章讲并发带来的四类数据不一致、封锁技术、两段锁协议和死锁。这是课程收官章，也是期末的重点章节。

一、并发执行带来的四类问题（必背）

问题场景（T1、T2 并发）后果
丢失修改T1、T2 同时读同一数据并各自修改一个的修改被另一个覆盖，凭空消失
不可重复读T1 读后 T2 修改，T1 再读同一事务两次读值不同
读脏数据T2 读了 T1 修改的值，T1 却回滚T2 拿到的是从未存在过的值
幻影读T1 按条件读后 T2 插入新行，T1 再按同条件读多出「幽灵」行
辨析要点：不可重复读针对「修改/删除已有数据」；幻影读针对「插入新数据」。读脏数据的关键词是「回滚」。选择题给场景要能对号入座。

二、封锁：S 锁与 X 锁

已加 S 锁已加 X 锁
请求 S 锁（读）✅ 可以（共享）❌ 拒绝
请求 X 锁（写）❌ 拒绝❌ 拒绝

相容矩阵记法：S 与 S 相容，其余都不相容。X 锁排他、S 锁共享——「读读可以并行，读写/写写不行」。

三级封锁协议（考频极高）

协议内容解决的问题
一级封锁协议修改前必须加 X 锁，事务结束释放防止丢失修改
二级封锁协议一级 + 读前加 S 锁，读完即释放+ 防止读脏数据
三级封锁协议一级 + 读前加 S 锁，事务结束才释放+ 防止不可重复读

三、两段锁协议（2PL）与可串行化

可串行化调度：多个事务的并发执行结果，与「按某种顺序串行执行它们」的结果相同——这是并发调度正确性的唯一准则。

两段锁协议保证可串行化：事务分两个阶段——扩展阶段（只加锁不放锁）和收缩阶段（只放锁不加锁）。 遵守 2PL 的调度一定可串行化，但 2PL 不能避免死锁（这半句话是判断题陷阱）。

四、死锁与活锁

  • 活锁：某事务一直抢不到锁（被不断「插队」）→ 预防：先来先服务
  • 死锁：T1 等 T2 的锁，T2 等 T1 的锁，互相等待成环 → 预防：一次封锁法、顺序封锁法；诊断：超时法、等待图（图中有回路即死锁）→ 解除：选一个代价最小的事务回滚
死锁诊断「等待图」：节点是事务，边是「等待」，回路 ⇔ 死锁。选择题给出等待图判断是否有死锁是常考题。与 OS 课程死锁知识的区别：数据库常用「诊断+解除」而非纯预防。

五、动手实践：模拟并发冲突

单连接的练习场模拟不了真并发，但可以模拟「两个事务先后加锁时的写覆盖」——丢失修改的雏形：

在本机 MySQL 中用两个终端窗口体验真并发（SQLyog/Workbench 也行）：

-- 终端1                                -- 终端2
START TRANSACTION;                      START TRANSACTION;
UPDATE account SET bal=bal+200
  WHERE id='A';                         SELECT bal FROM account WHERE id='A';
                                        -- 仍是旧值 1000！InnoDB 默认 REPEATABLE READ
                                        -- 读不到未提交修改 → 防了脏读
ROLLBACK;   -- 或 COMMIT;               COMMIT;
