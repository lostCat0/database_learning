恢复技术：断电、崩溃之后，数据如何自愈

硬件会坏、系统会崩、事务中途会断——恢复机制保证「把数据库恢复到故障发生前的一致状态」。 本章的核心是事务的 ACID 特性和「日志 + 转储」两套恢复技术。

一、事务与 ACID（必背）

事务（Transaction）：用户定义的一个数据库操作序列，要么全做、要么全不做，是不可分割的工作单位。

特性含义靠什么保证
原子性 Atomicity事务全做或全不做恢复技术（日志 UNDO）
一致性 Consistency执行前后数据库都处于一致状态原子性 + 完整性约束
隔离性 Isolation并发事务互不干扰并发控制（第11章，封锁）
持续性 Durability提交后的改变永久保存恢复技术（日志 REDO）
「ACID 各由什么机制保证」是简答高频：原子性/持续性→恢复子系统；隔离性→并发控制；一致性→完整性约束+前三者共同作用。事务的定义和 ACID 全称是名词解释常客。

二、故障的种类

  1. 事务内部故障：逻辑错误（除零、输入非法）或系统错误（死锁选中撤销）——最常见
  2. 系统故障（软故障）：断电、OS 崩溃——内存数据丢失，磁盘数据完好，未完成事务需撤销，已提交事务需重做
  3. 介质故障（硬故障）：磁盘损坏——外存数据丢失，破坏性最大
  4. 计算机病毒：人为故障

三、恢复技术：转储 + 日志

1. 数据转储（备份）

  • 按转储时状态分：静态转储（无事务运行时进行，简单但要停机）/动态转储（边运行边转，需配日志文件保证一致）
  • 按转储方式分：海量转储（全量）/增量转储（只转上次之后改变的部分）

2. 日志文件（Logging）

日志记录事务的开始、结束和对数据库的每一次修改（旧值/新值）。两条黄金法则：

  • 先写日志，后写数据库（WAL：先记下「我要改什么」，再做修改——日志是恢复的依据）
  • 恢复时：故障时未完成的事务 → UNDO（撤销，倒着做）；已提交但没来得及写盘的事务 → REDO（重做，顺着做）

3. 检查点（Checkpoint）

每隔一段时间，把日志缓冲区和数据库修改强制写盘并登记检查点。恢复时只需从最近的检查点开始查日志，而不必扫描全部日志——大幅缩短恢复时间。

最经典的简答：「系统故障后哪些事务要 UNDO、哪些要 REDO？」——故障时刻未提交的事务 UNDO；已提交但数据未写盘的事务 REDO。结合检查点时按「检查点前已提交 / 检查点后提交 / 活跃」三类判断（画出时间轴即可秒解）。

四、动手实践：亲眼看事务的原子性

再把 ROLLBACK 改成 COMMIT 跑一次，比较 COUNT 的差异——这就是「全做」与「全不做」两种结局。本机 MySQL 里可再体验：

USE school_practice;
START TRANSACTION;
UPDATE sc SET grade = 0;           -- 全表清零，假设这是误操作
ROLLBACK;                          -- 万幸，撤销
SELECT * FROM sc;                  -- 数据完好；换成 COMMIT 就真没了
