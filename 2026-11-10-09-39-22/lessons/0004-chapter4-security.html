数据库安全性：谁能看、谁能改

第3章你已经会写 SQL 了，但「会写」和「谁能写」是两回事。本章回答一个问题： 数据库如何防止非法使用和数据泄露。这章内容较轻，考点集中在几个概念的对比上。

安全性 vs 完整性（第5章）的辨析是经典简答题：安全性防止非法用户和非法操作（防外人），完整性防止合法用户输入不合语义的数据（防错误）。

一、数据库面临的安全威胁

  • 非授权用户恶意存取（窃取、篡改）
  • 合法用户的越权操作
  • 数据在存储、传输中被截获

数据库系统的安全模型一句话概括：先验明正身（用户鉴别），再查权限（存取控制），最后留证据（审计）+ 兜底（加密）。

二、安全性控制手段（考点主战场）

1. 用户标识与鉴别

系统提供的最外层安全保护。方式：用户名+口令、IC 卡、生物特征。每个用户在系统中都有唯一的用户标识。

2. 存取控制（本章最核心考点）

机制自主存取控制（DAC）强制存取控制（MAC）
权限由谁定用户自己定义（可授权、可收回）系统统一按密级强制执行，用户无权更改
SQL 支持GRANT / REVOKE主体（用户/进程）有许可证级别，客体（表/数据）有密级
规则授权者 ≥ 被授权者的权限许可证 ≥ 密级才可读；许可证 = 密级才可写
缺点权限可能被「转手」扩散过于严格、实现开销大
-- GRANT 语法（背下来）
GRANT <权限列表> ON <对象> TO <用户> [WITH GRANT OPTION];

-- 例：把查询 student 表的权限给 U1，并允许他转授
GRANT SELECT ON TABLE student TO U1 WITH GRANT OPTION;

-- 收回权限
REVOKE SELECT ON TABLE student FROM U1 [CASCADE | RESTRICT];
两个必背细节：① WITH GRANT OPTION 表示被授权者可以把权限转授他人；② 收回权限时转授链级联回收（CASCADE）——A 授权给 B，B 转授给 C，收回 B 的权限时 C 的也一并没了。

3. 视图机制

把敏感列/行藏在视图外，用户只能通过视图看到被允许的数据——第1章「外模式」的安全价值。视图机制是间接手段，最终还是要配合 GRANT 使用。

4. 审计（Audit）

把用户对数据库的所有操作自动记录到审计日志。审计是「事后追责」手段——因为启用审计很耗空间时间，通常作为可选设置。

5. 数据加密

防止数据在存储和传输中泄露：存储加密 + 传输加密。是最后一道防线。
